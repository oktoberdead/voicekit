# Архитектура первой версии

```text
USB mic / WASAPI event capture
    │ native PCM/float → mono
    ▼
bounded SPSC capture ring
    │ adaptive fractional reader → 48 kHz
    ▼
mic gain + mute ──────────────── dry monitor tap
    │
    ▼
pitch → ring mod → 20-band vocoder → echo → reverb
    │                               ↑ carrier synth / decoded file
    ▼
post-DSP mic mute
    │
    ├── + sound voices → output gain → soft safety knee → CABLE Input
    │
    └── monitor mix (dry / wet / sound independently)
                         │
                         ▼
                 bounded SPSC monitor ring
                         │ adaptive reader / independent clock
                         ▼
                    USB headphones
```

## Разделение

- **VoiceKit.Core** (`net10.0`) — не знает о WPF/NAudio/Windows. Неизменяемые настройки, DSP, буферы, вокодер, саундпад, команды/ID. DSP написан в репозитории, без стороннего pitch-движка.
- **VoiceKit.Windows** (`net10.0-windows`) — WPF, устройства WASAPI, декодирование через NAudio, драйверные события, хоткеи, трей и JSON-хранилище.
- **VoiceKit.Core.Tests** — xUnit: маршрутизация, ограничения выхода, drift/resync, starvation, очередь команд, поведение звуков, частотный smoke-test питча и отсутствие аллокаций графа в steady state.

## Владение потоками

1. **UI** публикует валидированные immutable settings/clip references через `Volatile.Write`; аудиограф захватывает snapshot один раз на блок. UI — единственный producer очереди звуковых команд.
2. **Capture** декодирует уже полученные байты PCM/float в заранее созданный SPSC ring. Файлы здесь не читаются.
3. **WASAPI render передачи** — единственный владелец mutable DSP state и плееров. На каждом блоке применяет очередь команд; смешивает передачу и независимый монитор. Не ожидает наушники.
4. **WASAPI render мониторинга** только читает отдельный ring с коррекцией частоты. Отставание мониторинга не блокирует передачу.
5. **Worker tasks** импортируют/декодируют файлы целиком. После загрузки массивы сэмплов не изменяются. Ограничения длины/общего кэша защищают от бесконтрольного постоянного потребления памяти, но не задают жёсткий пик памяти при декодировании.

SPSC-классы требуют именно одного producer и consumer. Producer при переполнении **не двигает read pointer**: так он не перезапишет сэмпл, который читает consumer. Consumer видит счётчик переполнения и удаляет устаревшую очередь. Для нормального дрейфа используется плавная коррекция ±0.5%; при очереди больше 4× target выполняется resync. Capture/monitor ring capacity — одна секунда сэмплов, рабочее заполнение значительно меньше.

`StopAll`/PANIC — отдельные атомарные флаги, а не команды, которые могут потеряться в полной очереди. Потеря key-up из-за переполнения очереди тоже запрашивает StopAll. PANIC проверяется и монитором: уже лежащий там звук не пройдёт после установки флага. Для снятия PANIC создаётся новый движок, состояние старых эффектов не восстанавливается.

## Задержки и измерение

- Pitch STFT: окно 1024 / hop 256, около одного окна алгоритмического запаздывания. Обход при нулевом сдвиге — прямой сигнал; фазовые/транзиентные артефакты при ненулевом сдвиге возможны.
- Vocoder: огибающие полос добавляют временное сглаживание, не длинную очередь.
- Echo/reverb: намеренные хвосты; основной dry путь не задерживается самим эффектом.
- WASAPI shared и возможное внутреннее преобразование формата NAudio/Windows добавляют собственные задержки. Целевая очередь и запрошенная WASAPI latency — разные составляющие.
- `ProcessingMs` измеряет наш provider Read, а не весь driver callback, и показывает последний блок, не гарантированный worst case. Счётчики показывают состояние нашего тракта, не внутренние буферы Discord/VB-CABLE.

## Управление и будущее API

`VoiceCommand`, `HotkeyBinding`, GUID звуков/пресетов задают словарь действий. Сейчас Windows dispatcher выполняет их из hotkey hook; экранные действия используют те же настройки/граф. Перед добавлением телефона стоит вынести UI-координацию команд из code-behind в отдельный application service и добавить сериализованный inbox: нельзя допустить второго producer у SPSC sound queue.

Сетевой транспорт намеренно отсутствует. Следующий этап: HTTP CRUD для библиотеки/пресетов/раскладок, WebSocket команд/состояния, локальное сопряжение и авторизация. Удержания с телефона должны иметь lease/heartbeat с гарантированным отпусканием при disconnect. Раскладки и вкладки мобильного редактора — отдельная схема, не массив координат внутри DSP-настроек.

## Ограничения восстановления

Остановка — идемпотентное освобождение выходов, capture и endpoints. Событие ошибки сначала ставит PANIC, затем передаёт обработку в UI; нельзя Dispose/Join собственного аудиопотока из его callback. Каждая попытка освобождения выполняется независимо. Устройство сохраняется по ID, а не имени; явной подмены на устройство по умолчанию после сбоя нет. Полноценного watchdog зависшего драйвера, recovery state machine и автоматического reconnect пока нет.
